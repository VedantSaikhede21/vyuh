## 2026-10-14 — Phase 0 spec clarifications

1. **Scenario shape follows the §4.4 example.** `schemaVersion` (not `version`), `roe` and `durationS` at top level, `environment = {date, time, isNight, weather, sunAzEl?}`, `request` optional. *Why:* the example is what scripted scenarios will look like; scripted scenarios have no ScenarioRequest.
2. **`Scenario.id` is a plain string; `scenarios.code` column added** (nullable unique, e.g. `S04`). *Why:* scripted scenarios have human codes, DB rows use UUIDs.
3. **`trackId` / `contactId` only at the top level of `SimEvent`**, not inside payloads; `SimEvent` is a discriminated union on `type`; `seq` required. *Why:* matches `session_events` columns and the §11.1 batch example; avoids two sources of truth.
4. **`session_events.seq` column with unique `(session_id, seq)`.** *Why:* replay ordering and idempotent ingestion need it.
5. **Scenario coordinates:** `x` = east, `z` = north, `y` = metres AGL; 2D points `[x, z]`. Flip to Three.js only in `sim-core/src/coords.ts`. *Why:* the spec mixed ENU and Three.js conventions.
6. **All enums in `enums.ts`**, including the ones §4 implied but did not list. `ACOUSTIC` omitted until implemented (adding an enum value later is non-breaking).
7. **Sensor and effector configs are unions keyed on `kind`.** `Penalty` and `PerContactMetrics` are provisional shapes until Phase 1 scoring; `threat_types.category` stays free text.
8. **Auth identity mapping.** Local: token `sub` = `users.auth_id` = `local:<email>`. Supabase: `sub` = Supabase user UUID; unknown users auto-provisioned as TRAINEE with no unit. Role always comes from the DB, never from token claims. *Why:* one code path for RBAC, and token claims cannot escalate privilege.
9. **No passwords in our DB.** Local mode uses `POST /auth/dev-login` (by email, disabled when `ENV=prod`); Supabase demo users are created in the Supabase dashboard. *Why:* `users` has no password column and Supabase owns credentials.
10. **Production guard:** `ENV=prod` requires `AUTH_MODE=supabase`; `LOCAL_JWT_SECRET` ≥ 32 bytes. Supabase project must use asymmetric JWT signing keys (JWKS cannot verify legacy HS256 tokens).
11. **sim-core RNG built in Phase 0** (spec lists it in Phase 1). *Why:* requested by the lead; it is foundational and has no dependencies.

## 2026-10-14 — Phase 0 tooling

1. **TypeScript pinned to ~6.0**, not 7.x. *Why:* typescript-eslint supports `<6.1`.
2. **zod 4** with built-in `z.toJSONSchema`. *Why:* no extra `zod-to-json-schema` dependency.
3. **One bundled JSON Schema (`$defs`) → one generated Python module.** *Why:* simple, deterministic codegen.
4. **`pnpm dev` = `pnpm -r --parallel dev`**, with a thin `apps/api/package.json` that calls uv. *Why:* no `concurrently` dependency.
5. **Sync SQLAlchemy 2 + psycopg 3.** *Why:* simpler than async; a unit-sized load is tiny.
6. **Stdlib logging (JSON lines) with a request-id contextvar**, not structlog. *Why:* no extra dependency.
7. **Line endings forced to LF (`.gitattributes`)** and datamodel-codegen run with `--disable-timestamp`. *Why:* Windows dev machines must not create diffs in CI's no-diff check.
8. **Tests use a real Postgres** (`vyuh_test` locally via docker compose, a service in CI). *Why:* tables use `jsonb` and `text[]`.
9. **Web auth guard is client-side** (token in browser storage, as Supabase JS does). Middleware-based guard is tech debt for later.
10. **Generated Pydantic enums use UPPER_SNAKE members** (`--capitalise-enum-members`) and unions get an explicit `discriminator` added by the JSON Schema export, so Pydantic uses tagged unions for `SimEvent` / `SensorConfig`. *Why:* readable Python, fast and precise validation errors.
11. **uvicorn runs in factory mode** (`app.main:create_app --factory`). *Why:* importing the app module must not require env vars (tests and tooling build their own `Settings`).
12. **Error code ↔ HTTP status map is duplicated in Python** and a pytest cross-checks it against `packages/shared/src/enums.ts`. *Why:* the map is a constant, not a type, and JSON Schema cannot carry it.
13. **Web uses system font stacks** (no `next/font/google`). *Why:* builds and runs fully offline.
14. **shadcn/ui components are added by hand** (`components/ui`, `components.json` present) instead of running the CLI. *Why:* the CLI is interactive and network-bound; output is equivalent.

## 2026-10-14 — Phase 1 (MVP loop)

17. **Phase 1 terrain is a procedural heightmap** (`PROCEDURAL_HILLS`: seeded 3-octave value noise, ~60 m relief, flat 400 m around the origin), not a flat plane. *Why:* exercises the same `sampleHeight` path that Phase 2 real-DEM presets use.
18. **Score scale:** the Phase 1 tree scores detection (25), classification (25) and decision (30); `total` is scaled to 100 over the components the tree scores (`componentMax > 0`), then penalties/bonuses are added and clamped to 0..100. Each component is the mean over scored threat contacts; a threat that was never detectable is excluded (SPEC §9.6). With no scored threat the base is full marks. `Score.componentMax` comes from the (immutable) tree file, so no DB column is needed.
19. **"Trainee detected" = first MARKED_DETECTED, CLASSIFIED, AFFILIATION_SET or RESPONSE_ORDERED** on any of the contact's tracks (TRACK_SELECTED does not count). *Why:* a trainee who classifies without pressing D clearly noticed the track; scoring them as "missed" would be unfair.
20. **Decision-tree format:** `if` nodes (metric/op/value), `bands` nodes (one leaf per band, then `next`), leaves with `component` + `points` or a session-level `adjust` (penalty/bonus, listed in `penalties`), `excluded` for fairness, and templated `feedback`. A pytest fails if any leaf lacks a test case.
21. **Enum additions:** `ContactOutcome.UNRESOLVED` (threat neither neutralised nor leaked at time-up) and `ResponseResult.NO_AMMO`. `PerContactMetrics` gains `trackIds` and `leaves`.
22. **EW_JAM / EW_SPOOF commands are rejected by `sim.dispatch` in Phase 1** (no EW effectors yet) rather than returning a fake outcome.
23. **Radar tracks associate by ground truth** (one track per radar × contact); confirmation is still N-of-M on noisy detections. *Why:* data association is out of scope for the MVP; the trainee still only sees track ids.
24. **Plausibility (SPEC §3.3) runs per batch and again on complete.** Extra rules beyond the spec list: contiguous `seq` (detects lost batches), first event is a matching SESSION_STARTED, no duplicate track ids, no events after SESSION_ENDED, and on complete the log must contain SESSION_ENDED with `endTMs` consistent. A failing batch is rejected whole and its `batchSeq` is not consumed.
25. **Responses embedding a Scenario or Score use `response_model_exclude_unset`.** *Why:* zod `.optional()` rejects `null`; explicit nullable fields (e.g. `endedAt`) are still sent as `null`.
26. **Real sim logs as API fixtures** (`apps/api/tests/fixtures/`, written by `packages/sim-core/scripts/export-api-fixtures.ts`); a sim-core test fails if they are stale. *Why:* API tests exercise exactly what the client sends.
27. **`MAX_EVENTS_PER_SESSION` is mirrored in Python** with a test cross-checking `api.ts` (same pattern as decision 12).
28. **Elo update on complete is deferred to Phase 5** (adaptive difficulty), where it is listed in SPEC §12.

## 2026-10-14 — Phase 2 Part A (terrain, LOS, day/night, EO/IR)

29. **DEM source: Copernicus GLO-30**, tiles downloaded from the public AWS bucket into `scripts/terrain/raw/` (git-ignored). Boxes: PUNJAB_PLAINS 30.520 N 75.700 E, JK_MOUNTAIN 33.750 N 75.875 E, 14 km each; vetted against OSM (no military / aeroway / dam / power features within box + 10 km; ≥ 50 km from IB/LoC). *Why:* free, global, 30 m, clear attribution terms.
30. **`heightmap.u16` is the load format; `heightmap.png` is a preview only.** Heights are stored relative to the origin elevation (absolute values in `meta.json`). *Why:* browsers' canvas decode is 8-bit, and a raw little-endian buffer needs no decoder; origin-relative heights keep the defended position near y = 0 so cameras and fog work for mountain presets.
31. **`buildings.geojson` uses local metres `[x, z]`, not lon/lat.** *Why:* the browser and sim-core need no projection library, and the coordinates match the DEM grid exactly. Default building height: 2 levels × 3 m when OSM has no `height` / `building:levels`.
32. **`scripts/terrain` is its own uv project** with its own CI step. *Why:* GDAL/osmnx are heavy and must not enter the API image.
33. **Preset meta is authoritative for the origin, and carries `utcOffsetMin`.** `environment.isNight` and `sunAzEl` are computed from suncalc and override stored values. *Why:* one source of truth; parsing a local time without an explicit offset would depend on the machine's timezone and break determinism.
34. **`World` object** (heightmap + buildings + LOS) passed to `createSim`; a bare `Heightmap` is still accepted. `PROCEDURAL_HILLS` stays as a built-in preset, so S01–S03 keep working.
35. **Radar LOS factor only in Part A** (clutter, rain, full model in Part B). A masked contact still consumes its fixed 5 random draws; the lost reason is `LOS` when every losing miss was masked.
36. **Camera pointing is sim state.** `CAMERA_SLEWED` gains an optional top-level `trackId` (lock — sim-core follows the track's estimated position each tick) and `payload.mode` (DAY/IR). *Why:* EO_IDENTIFIABLE depends on pointing and mode, so both must come from logged commands for exact replay. `mode` was added beyond the original approval list for the same reason (approved).
37. **Slew logging:** still throttled to 2/s, plus one final `CAMERA_SLEWED` at the end of every drag / slew / zoom / mode gesture so the sim settles on exactly what the trainee sees. **Known lag:** during a manual drag the sim's pointing can trail the view by up to 0.5 s, so EO_IDENTIFIABLE can be up to 0.5 s late while dragging. Accepted.
38. **EO/IR model constants (representative):** IR visibility cap = 1.5 × `visibilityM`; DAY mode yields nothing at night; IR cycles scaled by per-class `thermalContrast`; EO_IDENTIFIABLE hysteresis 1 s.
39. **`identifiableWhenClassified` keys off the scenario having an EO sensor**, not off any EO_IDENTIFIABLE being in the log. *Why:* a trainee who never pointed the camera classified before the contact was identifiable. Points are unchanged (wrong = 0 either way); only the leaf/feedback text differs if an old Phase 1 session is explicitly re-scored.
40. **Single canvas:** tactical and EO views are drei `<View>`s on one full-page canvas; the EO camera renders to a 640×360 target shown through a custom day/IR shader. *Why:* one WebGL context, one copy of terrain/buildings on the GPU.
41. **Terrain LOD:** 4×4 chunks with drei `<Detailed>` levels (step 1/2/4/8) and skirts; buildings merged into one geometry; a 100 m grid index for building LOS. *Why:* SPEC §16 draw-call and tick budgets.
42. **S11 / S12 are test scenarios** (tag `test`), separate from the S01–S10 training library.
43. **Scripted-scenario guard: 45 s minimum warning (was 60 s) plus "a scripted defence neutralises every threat".** *Why:* with radar LOS masking, S03 (20 m AGL, "less warning" by design) is first tracked at ~1,050 m instead of ~1,820 m, leaving 58.5 s; the guard's purpose is "defensible in time", which the new check tests directly. S01 and its API fixtures are unchanged; S02's second contact is tracked 2 s later.
44. **Tactical map lighting at night is a display aid.** The tactical view keeps a dusk-level ambient floor and an overhead "map light" when the sun is low or down; the EO/IR view keeps true darkness. *Why:* the tactical view stands in for a C2 map display, which an operator can always read; only the sensor view should be degraded by night.
45. **FPS is measured in headless Chrome on the integrated GPU** (ANGLE / D3D11, AMD Radeon on a Ryzen 7 5800H). *Why:* on a machine in use, a visible test window gets covered (Chrome throttles requestAnimationFrame to 1 Hz) or receives stray input; headless keeps the GPU path but removes both.

## 2026-10-14 — Phase 2 Part B (sensors, EW, scoring)

46. **Display-only seeder updates.** For a scripted scenario that already has sessions, `seed_scenarios` may update only `name`, `briefing` and `tags`, and only when every other content field is identical; any gameplay change is still refused (new code needed). *Why:* replay and scores depend on gameplay content, but wording fixes (e.g. S11/S12 ROE dashes) should not need a new scenario code. The "S01 mis-encoded dash" was a Windows console display artefact (cp1252 printing U+2014), not a data bug: seed files and DB hold a correct em dash.
47. **`RESPONSE_OUTCOME.collateral` is a list** (`{contactIds: string[]}`, was `{contactId}`). *Why:* one jam sector can affect several contacts. No stored event log contains `collateral` yet, so no `schemaVersion` bump.
48. **`SIM_VERSION`**: an integer exported by sim-core, bumped whenever sim behaviour changes. The client sends it on session create; `sessions.sim_version` stores it (nullable; older sessions are null). *Why:* Part B changes the sim, so old sessions will not replay exactly; Phase 4 replay must check the version instead of silently diverging.
49. **Class profiles reach Python as a generated file.** `pnpm gen:schemas` also writes `apps/api/app/seed/generated/class_profiles.json` (with a `_generated` key) from `CLASS_PROFILES`; CI's no-diff check covers it. `ClassProfile` gains `typicalLinks` (SPEC §7) and `category` (`DRONE` / `BIRD` / `MANNED_AIRCRAFT`, for `threat_types.category`). The scenario rules now require `rfActive: false` for `AUTONOMOUS_GNSS` / `FIBRE_OPTIC` / `NONE` links and `rfActive` for a `friendlyIdCode` (mirrored in Python). *Why:* one source of truth for threat data without Python reading `packages/` at runtime (there will be an API container without it).
50. **Rain is a two-way SNR loss, not a Pd factor** (accepted divergence from SPEC §6.1's "× rain factor"). Specific attenuation γ = 0.0101 · R^1.276 dB/km (representative X-band coefficients in the style of ITU-R P.838), loss = 2 · γ · range_km, subtracted from SNR before the logistic. Clutter stays as written (Pd × 0.4 below 15 m AGL inside 2 km). Neither adds random draws. *Why:* a fixed Pd factor would hurt a close target as much as a far one; path attenuation grows with range, as it does physically.
51. **2D alpha-beta track filter with per-tick prediction** (α 0.5, β 0.2; velocity from the first two measurements; Δt = time since last update). The HUD and the EO lock use the predicted estimate; track height stays the true AGL (tech debt "track height leaks truth" — radar height is not measured with noise, and a 3D filter would add an elevation draw). Measured 2026-10-14: on a constant-velocity target at ~3 km, position RMS 22/20/27 m filtered vs 33/38/37 m raw (seeds 1–3), velocity error converging from 11–39 m/s to 2.5–3.2 m/s; along S11's path, aiming at the filtered estimate puts the target within ±0.75° of bearing on 70 % of ticks vs 61 % for the raw measurement; a fully zoomed lock in the sim keeps S11 in frame 56 % of ticks (S12 57 %, S01 46 %) vs 43 % / 47 % / 44 % in Part A. No α/β (tried down to 0.15/0.02) keeps a target inside a 1.5° FOV: radar bearing σ 1° is larger than the ±0.75° half-frame. *Why:* the plan's "stays in frame" goal needs an EO tracker, not a better radar filter — added as step 4b (decision 52).
52. **EO video auto-track: MANUAL / CUE / TRACK camera states** (SPEC §6.2). Radar cues the camera at the filtered estimate (CUE); once the cued contact is at EO level ≥ DETECT inside the central half of the frame for 0.5 s the EO tracker takes over (TRACK) and aims at the contact itself plus a small deterministic jitter (stream `eo-track`, 1σ = 2 % of HFOV). TRACK breaks to CUE on leaving the frame, losing LOS, > 1 s with no EO level, or the contact going inactive (to MANUAL if the radar track is gone); a manual slew → MANUAL; a zoom / mode change on the same lock keeps TRACK. Pure sim state from logged commands, no new event; `SIM_VERSION` stays 2 (no sessions were recorded between steps 4 and 4b). Measured 2026-10-14, fully zoomed (1.5°): target in frame on 100 % of TRACK ticks in S11 (2,531 ticks, DAY), S12 (5,016, IR) and S01 (2,577, DAY), TRACK reached 13 s / 11 s / 16 s after the cue. API fixtures unchanged (the scripted player never moves the camera). *Why:* real C-UAS EO systems are radar-cued and then hold the target with a video tracker; radar bearing noise (σ 1°) alone cannot keep a 1.5° frame on target (decision 51).
53. **RF output = bearing strobes + a badge on radar tracks; no new events; RF-only contacts are not "detectable".** The RF detector (1 s scan, σ = `bearingErrDeg` / 2, LOS-masked, silent for non-emitting links) keeps strobes `E01…` in sim state; a radar track carries the nearest strobe within `bearingErrDeg` as a badge (band, friendly ID). Bearing-only association can mis-badge when two emitters line up — realistic ambiguity. *Why:* the trainee acts on tracks, not strobes, so strobes add evidence for identification without a new event type, and scoring stays fair (a contact the trainee could never act on is not penalised). No existing scenario has an RF sensor, so replays are unchanged and `SIM_VERSION` stays 2.
54. **EW_JAM / EW_SPOOF: a ±10° sector, not ROE-gated, success = NEUTRALISED, link-loss reactions** (SPEC §8). Sector toward the ordered track out to `rangeM`; every susceptible contact in it is rolled in id order (jam RF_MANUAL P 0.9, spoof AUTONOMOUS_GNSS P 0.8), friendlies and civilians included; affected non-target contacts go in `collateral.contactIds` and every affected contact gets `CONTACT_NEUTRALISED`. Jam reactions: attack run / swarm hover 5 s and land; others return home. Spoof: route drift growing to ~400 m. Defeated contacts keep flying, cannot reach an asset and count as resolved; an intercept on one is `NO_EFFECT` with no round used. EW is not gated by ROE or NO_KINETIC zones (SPEC §8 restricts only INTERCEPT). *Why:* matches the SPEC §8 effectiveness table and the jam-hits-friendlies constraint with simple, explainable geometry; the sector makes "check what else is on that bearing" a real decision.
55. **`FRIENDLY_JAMMED` −15 and `CIVILIAN_JAMMED` −5** (new `ContactOutcome` values, `default_v2` leaves). A friendly affected by a jam, targeted or collateral, is `FRIENDLY_JAMMED`; firing an intercept at a friendly stays `FRATRICIDE` −40. A civilian affected only as collateral is `CIVILIAN_JAMMED` ("check the sector before jamming"); a jam or spoof ordered on a non-threat's own track, or an intercept fired at it, is `WRONGLY_ENGAGED` −25. Precedence: FRATRICIDE > FRIENDLY_JAMMED > WRONGLY_ENGAGED > CIVILIAN_JAMMED. Birds are never penalised for EW orders (no RF link, nothing to jam); firing an interceptor at a bird is still `WRONGLY_ENGAGED`, as in v1. *Why:* jamming a friendly is serious but recoverable (it lands or returns), unlike shooting it; collateral on a civilian is a sector-awareness lesson, not a targeting error.
56. **UNAVOIDABLE excludes only the decision component; per-component denominators; no leak penalty.** A not-neutralised threat that reached an asset less than `max(shortest able effector cooldown, 10 s)` after it first became detectable gets an excluded `DECISION_UNAVOIDABLE` leaf; detection and classification still count. Tree leaves gain optional `excludeComponents`; the engine averages each component over the threats not excluded for it. Verified 2026-10-14 that `default_v1` re-scores identically: the two fixture logs, six golden cases (`tests/fixtures/v1_golden.json`, generated with the pre-change engine) and all three scored sessions in the local DB (28.8 / 60 / 100, full Score JSON equal). *Why:* SPEC §9.6 fairness — a pop-up threat inside one effector cycle says nothing about the trainee's decision, but they could still have detected and identified it; a separate leak penalty would double-count the lost decision points.
57. **Birds in `default_v2`: EW = 0 points but listed; intercept = −25.** Confirmed by the user 2026-10-15. A jam or spoof ordered on a bird costs nothing (a bird has no RF link, so nothing happens) but produces a `BIRD_EW_ORDERED` entry with 0 points and the feedback "this was a bird — check the spectrogram/EO before engaging", so the result screen and AAR still show the mistake; that bird gets no `NON_THREAT_IDENTIFIED` bonus and its response is not "appropriate". Firing an interceptor at a bird stays `WRONGLY_ENGAGED` −25, as in v1. Changed in `default_v2` before any session was scored with it (local DB: v1 scores only). *Why:* a wasted EW order is a discrimination error worth debriefing, but not a harmful act; a round fired at a bird is.

Used by the landing hero recording now and the Part 3a validator later; the test helper `playScripted` is unchanged. *Why:* one defender for media and validation, without changing existing guard tests.

## 2026-10-15 — Phase 3 Part 3a (generator, behaviours, ROE; `docs/plans/phase3a-plan.md`)

69. **`NO_KINETIC` is judged on the track's estimated position** (the filtered estimate, operator-known, decision 66), not the true contact position; a blocked order returns `BLOCKED_NO_KINETIC` (distinct from `BLOCKED_BY_ROE`) and spends nothing. ROE is checked first, then the zone, then cooldown/ammo. A point on a zone edge counts as inside. *Why:* intercepts resolve instantly when ordered, so the intercept point coincides with the track position; checking the estimated track position is equivalent to requirement §5 ("track or intercept point"), not a reduction of it. **If intercept time-of-flight is ever modelled, the check must move to the predicted intercept point.**
70. **`SIM_VERSION` 3.** (a) `DROP` waypoint: the payload is released (`CONTACT_DROPPED {x, z}`, once per contact) when the waypoint's hold ends, or on arrival when it has no hold — the SPEC's "hover 10–20 s, DROP, return" gives the trainee the hover window to act; a contact defeated by EW (hover-land, RTH or spoof drift) never releases. (b) `RTH` waypoint: after any hold, the contact switches to the existing RTH control (back to its first waypoint, despawn). (c) `WEAPONS_TIGHT` needs the trainee's classification to be a threat class **and** a HOSTILE call. (d) The `NO_KINETIC` gate (decision 69). (e) **Observed release:** `CONTACT_DROPPED` carries an optional top-level `trackId` only when the EO tracker was in TRACK on that contact's track (camera state from the end of the previous tick, as contacts move before the camera updates); the HUD shows `<trackId> PAYLOAD RELEASE OBSERVED` only then, otherwise the drop appears on the result screen only. The id is top-level, not in `payload`, per the event convention. Existing S01–S14 guard tests and API fixtures are unchanged under v3 (their scripted players classify and declare hostile). *Why:* the generator's SMUGGLING_DROP and ROE semantics need these in the sim; a release is not otherwise observable on these sensors.
71. **The ground-truth defender respects the new gates.** It never orders an intercept that ROE or a `NO_KINETIC` zone would block (zone judged on the track estimate, like the sim); in those cases it jams an `RF_MANUAL` threat or spoofs an `AUTONOMOUS_GNSS` threat if a ready effector is in range, otherwise it holds. *Why:* the 3a validator's "defender wins at D1–D3" must reflect what a correct operator could do, not what the sim would refuse.
72. **`default_v3`: a payload drop before neutralisation is a leak.** `metrics.py` sets `outcome = LEAKED` when `CONTACT_DROPPED` precedes any `CONTACT_NEUTRALISED`, and measures `warningS` (UNAVOIDABLE) to the earlier of the drop and reaching the asset. `default_v3` = `default_v2` plus two leaves: `DROP_BEFORE_NEUTRALISED` (feedback "Payload dropped before neutralisation (at N s).") and `DECISION_NEUTRALISED_AFTER_DROP` (15 decision points — engaged and killed it, but too late). Plausibility: a `CONTACT_DROPPED` before spawn is `DROP_BEFORE_SPAWN`; an observing `trackId` must already exist. *Why:* a delivered payload is the smuggler's mission accomplished, whatever happens afterwards. The rule is metric-level (shared by every tree) but `CONTACT_DROPPED` exists only in `SIM_VERSION` ≥ 3 logs, so v1/v2 re-scores are unchanged (golden test still passes) and the v1/v2 tree files are untouched. Known trust-boundary limit (as SPEC §3.3): a tampered client could omit the drop; replay validation in Phase 4 can catch it.
73. **Server-side terrain = `TERRAIN_DIR` + stdlib reader, cross-checked against sim-core.** `Settings.terrain_dir` defaults to the repo's `apps/web/public/terrain` (resolved from the API root, so it also works inside the image); the API image sets `/app/terrain` and copies only each preset's `meta.json`, `heightmap.u16` and `buildings.geojson` (Q1: buildings for `NO_KINETIC` siting), via `apps/api/Dockerfile.dockerignore` so other images' contexts are unaffected. `services/terrain.py` decodes the u16 with `array('H')`, samples bilinearly exactly like `sampleHeight`, and offers a coarse cell-centre grid for routing; it is never used for LOS or sensors. `packages/sim-core/scripts/export-api-fixtures.ts` also writes `apps/api/tests/fixtures/crosscheck/*.json` (heights now, sun times later), a sim-core test fails if they are stale, and pytest checks Python against them (±1 mm: sim-core stores float32). The compose `api` service sits behind a `profiles: ['api']` so `docker compose up -d` still starts only Postgres. *Why:* one source of truth for terrain with no duplicated binaries in git and no numpy in the API; the fixtures stop the Python copy of simple maths drifting from the sim.
74. **Generator design (`apps/api/app/services/generator/`, `GENERATOR_VERSION` 1).** A pure function `generate(GenerateRequest) → Scenario dict`. *Determinism:* every part draws from its own `random.Random` seeded from sha256(seed, name) (never Python's `hash()`); each planned contact group has a stable slot key (`threat:2`, `swarm:0`, `false:4`), so a regenerated or trimmed group never shifts the others; positions are rounded to 0.1 m and everything else to 0.01; `canonical_json` sorts keys; the scenario id is `GEN-` + a hash of the request. *Conditions:* SPEC §7.1 "Conditions" as (time band, weather preset) pairs per difficulty; DAY = sun ≥ 15°, DUSK = evening −4°…+6°, NIGHT = evening ≤ −12° (NOAA equations; ≥ 2° clear of the sim's −6° rule; within 0.21° of suncalc on the cross-check fixture); the date's month follows the weather preset's season; `DUST` is refused until a desert preset exists (Q8). *Composition:* single threats ATTACK_RUN / RECON_LOITER / SMUGGLING_DROP (night favours drops; D1 attack only); D3 may add a small group of 2–3, D4 one swarm + one decoy, D5 two or three swarms + one or two decoys on 2–3 axes; silent links are assigned by member count to reach the table's share (decoys stay RF-loud; swarm members share one link). Effectors: interceptor always (ammo = ceil(threats × factor)), jammer from D2, spoofer from D3; NO_KINETIC zones from D2 only (the D1 tutorial has no EW to fall back on). Low attack runs at D3+ take a least-exposure path on a 64 × 64 coarse grid (a ray-sampled visibility proxy, not LOS). *Duration:* last threat's critical point + 60 s, rounded up to 30 s, clamped 180–900 s, unless requested. *Cap:* SPEC §16's 60 entities, trimming false contacts, then flock members (min 3), then swarm followers (never below the table's threat minimum); oversized requests are clamped, not refused. *Checks at runtime:* geometry only (map margin, ≥ 5 m AGL, speed ≤ class max, spawn ≥ 1.5 km from assets for threats / 0.8 km for other non-friendlies), with up to 8 deterministic attempts per group; the result is validated by the generated Pydantic models and the Python cross-field rules. Sensor checks run in the sim-core validator in CI (approved: no Node in the API image). *Why:* SPEC §7 / §7.1 and requirements 3a.1 with as little machinery as possible; per-slot streams make tuning and retries local.
75. **Validator (`packages/sim-core/src/validate.ts`, CLI `pnpm --filter @vyuh/sim-core validate <file|dir> [--max-fail-pct N] [--json]`).** Checks: SCHEMA, HAS_THREAT, BOUNDS (200 m margin), MIN_AGL (5 m, except a DIVE end point or MSL waypoint), SPAWN_DISTANCE (threats 1.5 km, other non-friendlies 0.8 km), NIGHT_FLAG (stored `isNight` = suncalc), DETECTABLE (every threat gets a radar track in a passive run), WARNING_TIME, and DEFENDER_WINS at D1–D3 (the ground-truth defender, decisions 68/71, lets no threat reach an asset or drop). *Warning time* = a threat's critical point minus its first radar track, in a passive run: the critical point is reaching the asset or dropping; for a threat that does neither (recon orbit), the first moment it comes within 1 km of an asset; a decoy that never closes has none. Minimums by difficulty 60 / 50 / 45 / 40 / 30 s (SPEC §7.1 "warning time"; the scripted guard used 45 s). All S01–S14 pass (worst: S03 58.5 s at D2). The minimums live only in `validate.ts`; the Python generator does not duplicate them. *Why:* the sim is the judge of playability, so the sweep tunes the generator rather than a second sensor model, and the existing fairness rules (UNAVOIDABLE, decision 56) protect trainees from what slips through at runtime.
76. **Generator tuning for the seed sweep (keep the final approach in radar view).** First sweep: 29 % failures (mostly JK_MOUNTAIN: threats hidden by ridges until inside 1 km). Changes, each a heuristic that only biases geometry — sim-core still decides detection: (a) `visibility.py`, a terrain ray from the radar (30 m steps ≈ the DEM's 27 m for axis choice and siting; 100 m for the masked-route grid), ignoring buildings, Pd, clutter and noise; (b) the radar sits on whichever of the 10 highest points within 800 m of the asset sees most of three rings (1.5 / 2.5 / 3.5 km) at 30 m AGL; (c) each approach axis is turned (±60°) to the bearing whose final leg is most in view; (d) per threat, the straight final approach — attack/swarm: the last `reveal_s` × speed before the asset; recon: 1 km plus that; smuggler: before the drop — must be ≥ 85 % in view, else the threat flies higher (10 m steps, up to +60 m, never below the table's lowest altitude) and, failing that, turns (10° steps, ±60°; smugglers ±30° around the border axis so they still cross the border, which now follows the first smuggler's fitted bearing); (e) low threats from D3 are terrain-masked only beyond a reveal point (`reveal_s` 90 / 80 / 70 / 60 / 45 s by difficulty); (f) fast classes (FPV, loitering) stay ≥ 15 m AGL (radar clutter height); (g) swarm followers 20–40 m apart per rank and 0–5 m above the leader; (h) a decoy's orbit must be in view (its axis turns in 20° steps). The sweep uses separate seeds per difficulty (one unlucky effector roll must not fail every difficulty). Result on 2026-10-15: CI configuration (20 per difficulty, presets alternating) 1 / 100 failed; local 50 per difficulty 3 / 250 (1.2 %); all failures are JK_MOUNTAIN D4–D5 warning times. Margin: one more CI failure still passes (2 %), two more would fail — re-tune rather than raise the limit. Generation takes ~0.1–0.6 s per scenario. *Why:* the requirement is ≤ 2 % failing the sim's own checks; masking the outer route and revealing the last stretch keeps the SPEC's "terrain-masked attack" while guaranteeing the warning time a trainee needs.
77. **Ground-truth defender policy and a terminal-dive fix (both `SIM_VERSION` 3, before any v3 session).** Defender: (a) intercepts a moving threat only inside 55 % of interceptor range (Pkill ≈ 0.75; was 85 %, Pkill ≈ 0.54, which drained ammo at D1–D3 — SPEC §7.1 gives only 1–3 rounds per threat), or inside 85 % if it hovers (< 1 m/s, e.g. at a drop point); (b) jams an `RF_MANUAL` threat or spoofs an `AUTONOMOUS_GNSS` threat first, but only when no active non-threat on the same link is inside the ±10° sector (+2° margin) — so it never causes collateral (S14: it intercepts instead). It still never engages a non-threat (decision 68). Remaining inherent leak rate: a D1 attack run (3 rounds, no EW) is missed by all three ≈ 1 % of the time. Sim fix: a DIVE waypoint now starts the dive no later than the waypoint arrival radius, and completes only through the dive. Before, a fast, slow-turning class (e.g. LOITERING_GENERIC at 35 m/s, turn radius ≈ 100 m) whose arrival radius exceeded AGL × 1.5 "arrived" at its DIVE waypoint without diving and despawned beside the asset — it could never hit it. Quads are unaffected; S01–S14 guard tests and API fixtures are unchanged. *Why:* the validator's "defender wins at D1–D3" must measure scenario playability, not a wasteful defender; and a loitering munition that cannot hit its target was a sim bug.
